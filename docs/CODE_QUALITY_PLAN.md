# План улучшения качества кода Taskami

Дата: 2026-09-21. Проверенная база: `master`, коммит `48601e2`.

Документ предназначен для модели-исполнителя. Это план исправлений по результатам
обзора кода, а не отчёт о выполненных исправлениях. Код приложения при подготовке
плана не изменялся.

## Исходная проверка

- `build_run_sim`: успешная сборка, установка и запуск на iPhone 17 Pro / iOS 26.2.
- Полный `test_sim`: **182 passed, 0 failed, 0 skipped** — 165 unit и 17 UI.
- Просмотрены модель, парсер, query engine, редактор, файловые сервисы,
  интеграции, SwiftUI-оболочка, widget, настройки проекта и существующие тесты.
- Отдельные диагностические примеры с исходными Swift-файлами подтвердили:
  - после снятия `@done @done` модель считает задачу незавершённой, но после
    сериализации и повторного чтения она снова завершена;
  - снятие `@done` в `Task @doneLater @done` даёт `TaskLater @done`;
  - outdent + undo превращает соседние задачи A/B в A с дочерней B;
  - `createFile(named: "../...")` создаёт файл вне выбранного каталога;
  - `toggleDone` + `registerContentChange` оставляет `hasUnsavedChanges == false`.

Остальные замечания ниже установлены анализом цепочек вызовов. До исправления
исполнитель должен воспроизвести их тестом. Успешный существующий набор тестов
не означает, что перечисленные сценарии покрыты.

## Правила исполнения

1. Прочитать актуальный `AGENTS.md`, проверить `git status` и актуальность базы.
   Сохранить чужие изменения. Работать в отдельной ветке от актуального `master`.
2. Выполнять этапы по порядку, одним небольшим изменением за раз. Не запускать
   повторный общий аудит вместо реализации описанных регрессий.
3. Для изменения видимого поведения сначала добавить релевантный UI-тест,
   подтвердить его падение на старом коде, затем исправить. Выполнить
   `build_run_sim` и `test_sim` с `-only-testing:TaskamiUITests`, как требует
   `AGENTS.md`. Для чистой модельной логики добавить unit-тесты.
4. Не заменять падающий тест увеличением таймаута без доказанного сбоя окружения.
   Не проверять только accessibilityValue, если исправление касается сохранения:
   проверить файл и состояние после повторного открытия.
5. Новые тестовые файлы включать в соответствующий target
   `Taskami.xcodeproj/project.pbxproj`. Исходного `project.yml` больше нет.
6. Использовать изолированные временные документы и инъекцию файлового сервиса
   для ошибок/задержек записи. Не трогать пользовательские документы, Reminders
   и iCloud ради тестов.
7. Не делать одновременно архитектурную перепись, миграцию на Swift 6,
   обновление зависимостей и исправления поведения. Лицензия, Git-история,
   идентификаторы приложения и публикация не относятся к этому плану.
8. После каждого этапа записывать изменённые файлы, выполненные проверки и
   результат. Не объявлять выполненным этап с непроверенным критерием приёмки.
   В конце — полный `test_sim` и `git diff --check`.

## Этап 1 — Сохранение живого текста и корректное состояние документа

**Приоритет: P0. Выполнить первым.**

Файлы: `Taskami/Editor/TaskItemCell.swift`,
`Taskami/Editor/DocumentEditorViewController.swift`,
`Taskami/Services/DocumentService.swift`, `Taskami/Model/TaskDocument.swift`,
`Taskami/Views/DocumentView.swift`.

Проблемы:

- `textViewDidChange` передаёт текст в `cellDidChange`, но тот лишь выставляет
  dirty-флаг и запускает autosave. `item.content` не обновляется до commit.
  Поэтому autosave во время ввода сериализует старое содержимое, затем снимает
  dirty-флаг. Reuse активной ячейки вызывает dismiss без commit.
- Переключение Done и изменение даты через picker не гарантируют dirty-флаг:
  `registerContentChange` выставляет его только внутри обработчика undo.
- `save()` безусловно снимает dirty-флаг после `await`, даже если за время
  записи пользователь внёс следующую правку. Отмена debounce-задачи не отменяет
  уже начавшуюся `Task.detached` запись.

Работы:

1. Согласовать живой текст и модель до autosave; не нормализовать/переформатировать
   строку на каждый символ, чтобы не двигать курсор и не ломать IME.
2. Сохранить исходное состояние edit-session отдельно, чтобы undo оставался
   корректным после обновления модели во время ввода.
3. Централизовать отметку изменений: текст, теги, даты, структура, undo/redo.
4. Ввести ревизию документа и упорядочить записи одного документа. Снимать
   dirty-флаг только после записи той же ревизии; более новая правка должна
   оставаться dirty и попасть в следующую запись.

Приёмка:

- Ввод → ожидание debounce без закрытия клавиатуры → файл содержит новый текст.
- Ввод → reuse/выход из редактора → повторное открытие сохраняет текст.
- Done/дата делают документ dirty до записи.
- Искусственно задержанная запись A + правка B: A не помечает B сохранённой,
  конечный файл содержит B. Тест должен быть детерминированным, без случайных sleep.
- Сохраняются действующие тесты done-toggle, позиции строк и autocorrection.

## Этап 2 — Ошибки записи, закрытие и внешний доступ

**Приоритет: P0. Зависит от этапа 1.**

Файлы: `Taskami/Services/DocumentService.swift`,
`Taskami/Views/DocumentView.swift`, `Taskami/Views/ContentView.swift`,
`Taskami/Services/FileCoordinatorService.swift`.

Проблемы: autosave только пишет ошибку в лог; `DocumentView.onDisappear`
выполняет `try? save()` и затем безусловный `close()`. При конфликте или ошибке
записи изменённая модель теряется. Для внешнего документа `stopAccessing...`
вызывается в отдельном `onDisappear`, без ожидания завершения финального save.

Работы:

1. Сделать один владеющий процесс закрытия: commit → await save → close → release
   security-scoped access. Исключить гонку между двумя `onDisappear`.
2. При ошибке показать пользователю причину и действия повторить/сохранить копию.
   Не уничтожать последнюю копию несохранённого текста. Для неотменяемого закрытия
   предусмотреть локальный recovery draft; удалять его после успешной записи.
3. Сохранять `.pending`, если загрузка выбранной внешней версии не удалась.
4. Обработать уход в background без опоры только на односекундный debounce.

Приёмка: инъекция ошибки записи и внешнего конфликта не теряет данные; повторная
запись восстанавливает нормальный режим; внешний файл сохраняется до освобождения
доступа; UI сообщает об ошибке, даже когда документ уже отображён.

## Этап 3 — Безопасность дерева и drag-and-drop

**Приоритет: P0. Можно выполнять после этапа 2 независимо от интеграций.**

Файлы: `Taskami/Model/TaskDocument.swift`,
`Taskami/Editor/EditorDragDropHandler.swift`,
`Taskami/Editor/DocumentEditorViewController.swift`.

Проблемы:

- Drop берёт индекс из отображаемого списка, но обращается к `document.allItems`.
  После folding/filter/focus эти позиции обозначают разные элементы.
- `moveItem` допускает родителя, равного самому узлу или его потомку. Это создаёт
  цикл, после чего рекурсивное обновление отступов не может завершиться.
- `item(atPath:)` проверяет только верхнюю границу. Отрицательный индекс из
  `.foldstate` попадает в индексирование массива; индексы перемещения также
  ограничиваются только сверху.

Работы: разрешать drop по ID из snapshot; до удаления узла проверять принадлежность
дереву, отсутствие цикла и допустимость индекса; определить вставку в конец и
смещение при переносе внутри одних siblings; отрицательные пути возвращают nil.

Приёмка: unit-тесты self/descendant/no-op/negative/out-of-range moves без изменения
дерева при отказе; UI-тесты reorder после folding, фильтра и focus; список ID,
parent-ссылки и уровни отступа остаются согласованными.

## Этап 4 — Внешние изменения должны обновлять редактор

**Приоритет: P1. Зависит от этапов 1–2.**

Файлы: `Taskami/Services/DocumentService.swift`,
`Taskami/Editor/DocumentEditorView.swift`,
`Taskami/Editor/DocumentEditorViewController.swift`.

`reloadFromDisk()` заменяет `document.items`, создавая новые UUID, но сохраняет
`document.id`. `updateUIViewController` вызывает `setDocument` только при изменении
этого id. UICollectionView остаётся со старым snapshot. Сам по себе `@Observable`
не применяет snapshot в UIKit.

Работы: явная ревизия/сигнал замены содержимого; после reload обновлять snapshot,
сбросить устаревшие editing/focus/undo ссылки; обновить lineEnding вместе с encoding.
Не вызывать полный reload на каждый символ. Защитить reload от правки, сделанной
во время его `await`.

Приёмка: изменение файла снаружи меняет видимые строки без переоткрытия; новые
строки редактируются; dirty-документ сначала показывает выбор версии; неудачная
загрузка сохраняет локальные данные и состояние конфликта.

## Этап 5 — Настоящие undo/redo для структуры и содержимого

**Приоритет: P1. После этапов 1 и 3–4.**

Файлы: `Taskami/Editor/DocumentUndoManager.swift`,
`Taskami/Editor/DocumentEditorViewController.swift`,
`Taskami/Editor/TaskItemTextView.swift`.

Проблемы: отдельный `docUndoManager.undoManager` не подключён к responder chain;
обработчик undo только обновляет snapshot и fold-state, не запускает autosave.
Обратный вызов indent/outdent не всегда восстанавливает прежнее дерево, потому что
outdent переносит следующих siblings в children. Не сохраняется прежний тип строки;
вставка в корень и drag-and-drop не имеют полноценной регистрации undo.

Работы: подключить document undo manager к действиям интерфейса; сохранять точное
состояние изменённой структуры (parent, позиция, перемещённые siblings), тип и теги;
не создавать undo для no-op; после undo/redo синхронизировать модель, экран и файл.
Развести посимвольный undo UITextView и структурный undo документа.

Приёмка: outdent A из `Parent: [A, B]` → undo полностью восстанавливает соседство;
redo воспроизводит перемещение. Проверить add/delete/move/type change, no-op indent,
сохранение результата после переоткрытия и реальные пользовательские Undo/Redo.

**Приоритет: P1.**

Файлы: `Taskami/Model/TaskItem.swift`, `Taskami/Parser/TagParser.swift`,
`Taskami/Parser/DateTagParser.swift`,
`Taskami/Editor/DocumentEditorViewController.swift`.

Работы:

1. Удалять теги по диапазонам парсера с конца строки, не через substring search.

расположение в начале/середине/конце, round-trip; UI-фильтр `not @done` обновляется
после toggle, `@done` — после undo; дата после Return нормализуется как после dismiss.

## Этап 8 — Reminders: разрешения, ошибки и идентичность задач

**Приоритет: P1.**

Файлы: `Taskami/Info.plist`, `Taskami/Services/RemindersService.swift`,
`Taskami/Views/DocumentView.swift`.

Проблемы: вызывается `requestFullAccessToReminders`, но есть только устаревший
`NSRemindersUsageDescription`; `saveCalendar` и `save(reminder)` подавляют ошибки;
сопоставление по `item.content` включает изменяемые теги и смешивает одинаковые
задачи из разных документов; `store.sources.first!` допускает падение.

Работы: добавить `NSRemindersFullAccessUsageDescription`; убрать force unwrap;
передавать ошибки в SyncResult; считать только успешно сохранённые операции.
Ввести устойчивую связь документ/задача/reminder через отдельное хранилище mappings
или явный сохраняемый идентификатор, не через случайный UUID повторного парсинга.
Если выбран sidecar, определить поведение при rename/move. Не удалять произвольные
напоминания пользователя. Оставить текущий односторонний экспорт.

Приёмка: тестовый адаптер EventKit проверяет отказ доступа, отсутствие источников,
ошибки save/commit; повторная синхронизация, изменение даты/Done и две одинаковые
задачи не создают ошибочных дублей и не обновляют чужую задачу.

Справка Apple:
[requestFullAccessToReminders](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoreminders(completion:)),
[NSRemindersFullAccessUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsremindersfullaccessusagedescription).

`TaskamiWidget/WidgetDataStore.swift`, `TaskamiWidget/TaskamiWidget.swift`,

Для настоящей агрегации по всем документам потребуется отдельная задача.

Вынести общий Codable-контракт в один файл обоих targets; добавить идентичность
строк внутри снимка; использовать Calendar для следующей полуночи. Ограничить
частоту WidgetCenter.reloadTimelines при посимвольном вводе.

Приёмка: тесты с внедряемыми часами на смену суток/DST, одинаковый текст, смену
документа и удаление источника; снимок widget не показывает вчерашние задачи как
сегодняшние. Проверить общий App Group в симуляторе.

## Этап 11 — Query engine, производительность и сборка

**Приоритет: P2, после исправлений сохранения и дерева.**

Файлы: `Taskami/Query/*.swift`, `Taskami/Model/TaskDocument.swift`,
`Taskami/Editor/DocumentEditorViewController.swift`,
`Taskami/Editor/TaskPaperTextHighlighter.swift`, `.github/workflows/ios.yml`,
`Taskami.xcodeproj/project.pbxproj`, `README.md`.

Работы:

1. Определить поведение неверных/неполных запросов. Сейчас parser не требует
   потребления всех токенов и закрывающей скобки, а compile при nil возвращает
   «совпадает всё». Добавить явный результат разбора/ошибку и тесты, сохранив
   удобство живого ввода. Не вводить молча новую грамматику.
2. Проверить `index` для корневых элементов: сейчас все возвращают 0.
   Зафиксировать документированную семантику и передавать контекст документа.
3. Измерить открытие/прокрутку/фильтр на 1 000 и 10 000 строк. По результатам
   убрать повторную полную flattening при каждом `item(withID:)`, компилировать
